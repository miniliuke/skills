# 环境、编排与日志

## Docker / Compose

固定镜像版本；生成本次独有的 Compose project name（可使用运行器的 IT_RUN_ID），不写共享 container_name。服务间使用 Compose DNS 和容器端口，宿主调用使用发现的映射端口，避免固定端口冲突。数据用一次性卷或专用 schema。

环境脚本显式执行 `docker compose -p <本次名称> -f <项目文件> up -d`，通过 healthcheck/健康接口/数据库查询等待就绪；超时收集 ps、health 和 logs。多服务按依赖启动，可用 Compose 管理并发服务生命周期，测试步骤保持清晰顺序。

先采集 `docker compose ... logs --no-color --timestamps`，再对同一 project 执行 down；`--volumes` 仅限本次创建的专用卷。禁止全局 prune。即使 up 部分失败，也尝试清理已创建资源。Docker 不存在、daemon 不可用或镜像无法获取时报告阻塞。

## 本地或混合环境

用项目虚拟环境、wrapper、固定依赖和测试 profile；不要全局升级依赖。依赖可在 Docker 中、应用在宿主启动；多实例分别记录配置和 PID/进程句柄、端口、工作目录与日志位置。

启动脚本应保存归属记录，清理前验证进程身份，不能按进程名/占用端口批量 kill。优先现有进程管理器；长驻进程重定向 stdout/stderr 至本次产物目录。服务启动要交由环境脚本或 Compose 管理，不把长驻命令放到有限时的普通测试步骤。

复用用户指定的本地服务时记录为 external，不停止它；只清理明确属于本次运行的数据。配置 `.env.example` 使用虚构值，真实凭据通过环境或受忽略的本地配置注入。权限来自用户任务和现有环境，不能借本技能扩大访问范围。

## 编排与失败语义

预检（运行时、Docker、端口、配置）失败为环境阻塞；setup/ready/seed 失败使后续业务用例阻塞。依赖失败时不能继续写业务数据。独立用例可继续，但每条用例的后续依赖步骤应停止。

业务失败先保存现场再清理；采集失败也要清理，清理失败保留原始测试结果并单独报错。Ctrl-C/TERM 使用 finally/trap；强制 kill 或宿主崩溃无法保证清理，保留 run_id 和资源标记供恢复清理。保留现场必须由用户选择并明确给出回收命令。

AI 可根据结构化结果决定选择诊断探针或重跑范围；固定的状态转换与等待写入脚本即可。不要为流程编排搭建多代理系统。

## 日志预算

默认 stdout 仅报告阶段状态、数量、失败 ID、耗时和产物路径。完整原始日志留在本地受忽略目录；AI 首次只读摘要，失败时读取少量脱敏片段（建议每个失败 40 行、总计 200 行内，必要时按证据扩大）。

除了测试运行器日志，必须采集服务、数据库、队列/容器日志及必要的请求响应/SQL 差异。记录统一时间、run_id/case_id/trace_id；原始日志中保留 Java 异常 cause 链，按时间窗口、异常签名和错误次数在脚本中去重。

不要只按 ERROR 判断失败：负面用例可能预期报错；断言才决定通过。模型区分连接失败/环境阻塞、fixture/断言缺陷与业务缺陷，不根据最后一行猜根因。

采集阶段在把任何内容交给模型、CI 或外部服务前脱敏密码、Authorization/Cookie、连接串凭据、令牌和业务个人数据。运行器只能遮蔽部分常见字段和显式 `redact_env` 值，不能替代项目级脱敏。raw 日志可能含密钥，不提交或自动上传。
